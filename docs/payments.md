# 支付模块：第一版

第一版用于会员购买商品或服务的一次性付款：多个内容规格、多件数量、单币种订单、PingPong 托管收银台、支付通知与主动查询、全额退款、人工交付状态。支持实体商品、数字商品和服务。分类开启在线销售后，直接在原内容中配置规格和价格，复用内容标题、介绍和封面，无需另建售卖项列表；主题负责展示和购买入口。独立 React 购物前台提供购物车与结算，详见 [购物前台接入](storefront.md)。暂不包含库存、运费、税费、优惠券、订阅、分账、自动发货、自动开通权益、部分退款、拒付处理及结算账单对账。

## 内网开发与沙箱配置

在“支付管理 → 支付渠道 → 添加 PingPong”中选择“沙箱测试”，点击“填入官方沙箱参数”，可带入官方公开的 Client ID、accId、Salt，并选中启用渠道；填写本站公开地址、核对币种后保存。下载配置示例也包含相同公开测试参数，`public_url` 留空等待填写，不使用示例域名代替本站地址。

当前官方示例测试卡为 `5204740000001002`，有效期填未来年月、CVV 为任意三位数字；若出现 3DS 验证，验证码为 `1234`。公开测试账号可能被多人共享，稳定联调可向 PingPong 申请专属沙箱账号。测试参数与卡资料来源见 [官方沙箱说明](https://acquirer-api-docs-v4-en.pingpongx.com/notes/zh/onlinePayment/sandbox/)，实际可用性以官方返回为准。

没有公网 IP 时，可使用 HTTPS 内网穿透，将公开 HTTPS 域名转发到本机 GoCMS（开发环境通常是 `127.0.0.1:18080`）。后台网站公开地址填写该域名，返回路径保持 `/shop/orders`；来自 PingPong 的通知与用户付款后跳转均通过此域名进入本站。应使用自己控制的测试入口，只公开购物应用、交易接口和所需静态资源，后台管理入口不应通过临时隧道开放。隧道地址变化时新增渠道或复制为新配置，保留旧渠道用于历史交易。

本仓库提供开发转发层 `scripts/payment-sandbox-proxy.py`，通过 `--site` 指定测试站点，默认仅监听 `127.0.0.1:18081`、转发至 GoCMS `18080`。示例：

```sh
python3 scripts/payment-sandbox-proxy.py --site <测试站点ID>
cloudflared tunnel --no-autoupdate --url http://127.0.0.1:18081 --protocol http2
```

将 tunnel 输出的 HTTPS 地址填入后台渠道的公开地址。转发层仅放行购物前台、会员登录注册、公开地理查询、交易接口、支付通知和必要静态资源；屏蔽管理 API、后台、原始数据目录及任意 Vite 文件读取。它固定站点范围，并移除管理会话 Cookie，不修改支付签名或订单状态。此工具仅用于开发联调，不支持 Vite 的 WebSocket 热更新。

临时域名与本机地址的登录状态、购物车彼此独立；在本机下单后跳回临时域名，可能需要使用同一会员账号重新登录查看订单。关闭隧道后公开地址失效，重启通常获得新域名，原渠道不会自动更新。结束测试后在后台停用该渠道，再停止隧道与开发转发层。

纯内网地址不能用于验证异步通知，不能把“渠道已保存”视为完成支付联调。订单页支持主动同步状态，系统也会定期查询待确认交易，但生产及完整沙箱验收仍需检查通知链路。参见 [PingPong 支付通知接入说明](https://acquirer-api-docs-v4-en.pingpongx.com/notes/zh/guide/paymentNotify/)。

## 启用

1. 向 PingPong 申请 **Checkout 独立站收单**及沙箱参数，确认已开通的币种、付款方式和生产区域。普通跨境收款账户不等于已开通 Checkout。官方提供 [托管收银台接入](https://acquirer-api-docs-v4-en.pingpongx.com/en/notes/integrate/link/)、[服务端地址](https://acquirer-api-docs-v4-en.pingpongx.com/en/notes/guide/endpoint/)及 [v4 签名规则](https://acquirer-api-docs-v4-en.pingpongx.com/en/notes/guide/sign/)。
2. 超级管理员进入“支付管理 → 配置支付密钥”，选择“自动生成（推荐）”或导入已有密钥。自动生成使用服务端安全随机数；导入值必须是 **32 字节随机密钥的标准 Base64 编码**。密钥保存到 `-data` 指定目录的 `payment.key`，权限为 `0600`，保存后立即生效，重启自动读取。导入支持选择 `.key` / `.txt` 备份文件或粘贴原值。保存后在“密钥管理与备份”下载备份文件；页面不回显密钥，也不提供直接覆盖操作。未配置时 CMS 正常运行，不能新增或使用支付凭据。
3. 后台进入“支付管理 → 支付渠道 → 添加 PingPong”，填写 Client ID、店铺编号 `accId`、签名 Salt、沙箱环境、币种、本站 HTTPS 公开地址和付款返回页面路径。公开地址只填源站，例如 `https://shop.example.com`；独立购物前台的返回路径填 `/shop/orders`；自定义主题也可填写其实际发布的结果页路径。也可下载 JSON 配置示例，填写后从后台导入，核对表单后保存。导入只接受可配置字段，不会导入渠道 ID 或站点归属。系统为渠道生成独立通知地址，在后台展示并随交易请求传给 PingPong。更换参数可点击“复制为新渠道”，重新填写 Salt 后保存，旧渠道保留处理历史交易。
4. 在“分类管理”开启“允许本分类内容在线销售”，再进入该分类的“内容管理”，先在侧边栏“规格维度”中维护名称、类型、单位及候选值，再在内容编辑的“在线销售与规格价格”中选择已有维度、类型和币种，填写价格表。维度支持选项、文本和数字，供当前站点的内容复用；每行是一个实际售卖组合，各自配置价格、编号和启停。不区分规格时无需添加维度，保留一行标准规格即可。编号留空自动生成。每条内容最多 12 个维度、500 个组合，不允许重复编号或重复参数组合。销售配置与内容在同一事务保存，出错时一起回滚。
5. 为内容设置封面，可用原有上传、素材库入口或公开 HTTPS 地址；素材操作需要 `media` 权限。本站图片须为当前站点已登记的有效素材，付款时以渠道的网站公开地址补齐 HTTPS 地址。有效规格和历史订单引用的图片不能直接从素材库删除。每条内容的规格共用一个币种，只有同币种的已启用渠道能支付。价格以最小货币单位整数保存；JPY 为整数，其他已支持币种为两位小数。商户实际可收币种以 PingPong 开通结果为准。
6. 使用内置独立购物前台时，直接访问 `/shop/`，无须安装购买模板或发布交易页面。若使用主题自己的购买页面，可在支付页面点击“安装购买模板”（需要 `theme` 权限），然后在后台分类配置中选择 `payment_checkout.html` 作为封面模板，设置发布路径并发布。已有同名文件时保留原文件，可到主题管理中编辑；也可从主题管理导入包含自定义购买页面的主题 ZIP。发布后在沙箱完成下单、付款、通知、查询、退款及重新启动恢复测试。检查公网能够访问 `/api/payments/webhooks/<渠道公开ID>`，反向代理应将该路径及 `/shop/`、`/api/commerce/`、会员接口转发给 Go 服务，且不缓存响应。生产渠道应在商户审核通过后使用独立配置创建。

当前传给 PingPong 的 `shopperIP` 取 Go 服务的直接连接地址，不信任任意客户端传入的转发头；反向代理部署时该地址可能是代理 IP。第一版尚未提供可信代理网段配置，正式风控联调时需确认这一限制。

密钥用于 AES-GCM 加密数据库里的 Salt，并绑定站点和渠道身份。它由超级管理员统一管理，所有站点共用；普通站点管理员和 API Key 均不能初始化、导出或接管。`payment.key` 与数据库需要分别备份，不能提交到仓库、放进主题包或公开目录；服务启动时检查数据目录与公开资源目录的位置关系。后台密钥接口为 `POST /api/admin/payments/key`，请求体为 `{"mode":"generate"}` 或 `{"mode":"import","key":"..."}`，只返回保存结果。`GET /api/admin/payments/status` 只返回配置状态、来源、是否可初始化、导出、接管及是否需恢复。导出接口为 `POST /api/admin/payments/key/export`，返回不可缓存的下载附件；接管环境变量为 `POST /api/admin/payments/key/adopt`。这些接口要求超级管理员后台会话及同源请求。

仍兼容部署环境配置的 `GOCMS_PAYMENT_KEY`。尚无本地密钥文件时使用环境变量，可在“密钥管理与备份”点击“接管到后台管理”，将当前同一密钥保存到独立文件，无需手动修改环境变量或重启。重启时文件优先，环境变量作为无文件时的兼容来源。下载或接管前会验证来源密钥与当前生效密钥一致，不改变商户凭据和历史交易。已有渠道时禁止重新生成，导入前会验证该密钥能够解密全部站点的历史凭据；错误密钥不会写入。加载文件或环境变量时也会验证历史凭据，格式错误、文件权限过宽或不能解密会阻止服务启动。

密钥丢失后无法通过新建密钥恢复历史凭据；更换密钥需要另行实现凭据重加密，目前不提供在线轮换。已有渠道只允许修改名称与启停；更换商户凭据、区域、币种或回跳地址时新增渠道，保留旧渠道处理历史交易。停用渠道后仍处理历史查询和通知。

## 主题接入

商品列表、详情和规格选择继续复用主题生成的 HTML，选好规格后提交至 `/shop/cart/add`。独立 React 应用仅负责购物车、结算、订单结果及登录注册，不提供商品列表。Blue 主题和默认详情模板已引用 `commerce-purchase.html`，提供规格、数量和购物车按钮；自定义主题的片段及表单接入示例见购物前台说明。购物前台及交易 API 无需重新发布 HTML，开发与部署见 [购物前台说明](storefront.md)。

默认模板目录另提供 `payment_checkout.html` 单规格示例，包含会员登录/注册、选择内容及规格、下单、跳转和结果查询。通过分类的 **封面模板绑定**选择它，并按配置设置发布路径；系统不根据分类名或 URL 自动绑定。使用独立主题时，可通过支付页面的安装入口将内置模板加入当前主题的 `templates/`，再在主题管理中调整样式，或按以下 API 自行实现并导入主题包。安装不会覆盖同名文件；继承主题的站点会先创建本站主题副本。更新程序不会自动覆盖已有外部主题。

购买页面及返回页面必须和会员接口同源，并能调用动态 API。页面读到 `payment_order` 参数时只按该编号请求服务端确认结果；参数、跳转成功、用户截图都不能直接触发交付。目录 API 每页返回最多 50 个规格，默认示例展示第一页；主题可以按 `page=N` 翻页，并用 `category_id` 筛选直接所属分类（不含子分类），或用 `content_id` 筛选一条内容。内容详情页的购买链接可指向后台配置并发布的购买页面，附加 `?content_id=<内容ID>`；示例会只加载该内容的规格。核心不固定购买页面路径，也不自动修改已有主题的购买按钮。

| 接口 | 用途 |
| --- | --- |
| `GET /api/commerce/channels` | 不含商户凭据的已启用付款渠道，不加载商品目录 |
| `GET /api/commerce/storefront` | 当前站点 ID、后台配置的站点名称与购物前台路径 |
| `GET /api/commerce/variants?ids=1,2` | 按最多 50 个规格 ID 重新读取可购买数据，不可购买的规格不返回 |
| `GET /api/commerce/catalog?page=1` | 当前可购买的内容规格和不含商户凭据的渠道列表；支持 `content_id`、`category_id` 筛选 |
| `POST /api/commerce/orders` | 登录会员创建订单，必须带 `Idempotency-Key`（16–128 字符） |
| `GET /api/commerce/orders` | 当前会员订单列表 |
| `GET /api/commerce/orders/<id>` | 当前会员自己的订单及支付、退款记录 |
| `POST /api/commerce/orders/<id>/pay` | 请求体 `{"account_id":1}`，返回支付记录及 `payment_url` |
| `POST /api/commerce/orders/<id>/sync` | 主动查询待确认支付，再返回订单 |

多明细创建订单示例见 [购物前台 API 约定](storefront.md)。下列旧单规格请求仍兼容：

```json
{
  "content_id": 1,
  "variant_id": 1,
  "quantity": 1,
  "email": "buyer@example.com",
  "customer_name": "Buyer Name",
  "address": {
    "street": "123 Example Road",
    "city": "Example City",
    "state": "CA",
    "postcode": "90001",
    "country": "US"
  }
}
```

订单新增 `items` 数组保存每行快照；旧 `item` 字段保留第一行，`quantity` 为所有明细的数量合计。后台详情展示全部明细。已有单规格订单迁移为第 1 行，订单编号和支付记录不变。

实体商品要求完整收货地址，`state` 可选；数字商品和服务不要求地址。金额由服务端读取规格售价计算，并验证规格属于该内容、站点匹配、所属分类开启销售、内容公开且内容及规格均启用。分类开关只作用于直接所属内容，子分类需分别开启；关闭分类、隐藏内容或移除规格会停止新订单购买。订单保存内容 ID、规格 ID、规格编号及参数、名称、封面、类型、币种、单价、数量和地址快照，后续改价不改变旧订单；已创建的未付款订单仍按原快照继续付款。同一会员、站点、幂等键及相同请求返回同一订单；相同键对应不同输入返回 409。下单结果不明时保留原请求和原键重试。支付网络超时后保留原订单和交易编号，先同步确认，避免另建订单重复收款。示例在同一浏览器标签页的 `sessionStorage` 中保留重试信息，其他设备可通过会员订单接口找回。

## 后台权限与操作

侧边栏入口需要 `payments`；账户读取与配置另需 `payments.configure`；发起退款另需 `payments.refund`；变更交付另需 `payments.fulfill`。超级管理员默认可用，普通用户组需显式授权。支付写操作要求后台会话及同源请求，不接受 API Key 写入。所有数据按当前站点授权隔离。分类销售开关及内容规格配置还需要对应分类／内容操作权限；公开内容的修改仍需要 `content.review`。销售配置只接受有 `payments` 权限的后台登录会话及同源请求，不接受 API Key 修改价格。

后台可查询订单、同步支付、对每笔成功交易发起一次全额退款、同步退款，并维护“等待交付／正在交付／已完成／失败”的交付状态。退款成功不会撤销已经发生的实体发货或服务交付，相关业务需人工处理。交易历史不提供删除入口，站点存在交易数据时不能直接删除。

后台 API 前缀 `/api/admin/payments`：`status`、`accounts`、`offers`、`orders`、`events` 提供读取；`accounts` 提供创建；`accounts/<id>` 提供 PUT；`orders/<id>/fulfillment` 提供 PUT；`attempts/<id>/sync`、`attempts/<id>/refund`、`refunds/<id>/sync` 提供 POST；`checkout-template` 提供 POST，显式安装内置购买模板，不自动绑定分类或发布。列表每页 50 条（账户最多返回 100 条）。回调记录仅保留去重摘要、交易编号、事件类别及状态，避免储存完整支付敏感报文。

分类接口通过 `commerce_enabled` 开关销售；原有内容保存接口通过可选的 `commerce` 对象保存交易配置，省略该字段会保留已有配置：

```json
{
  "enabled": true,
  "kind": "physical",
  "currency": "USD",
  "dimensions": [
    {"key": "dim_diameter", "name": "口径", "type": "select", "unit": "", "options": ["DN15", "DN20"]},
    {"key": "dim_material", "name": "材质", "type": "select", "unit": "", "options": ["不锈钢", "铸铁"]}
  ],
  "variants": [
    {
      "id": 0,
      "sku": "",
      "specifications": [{"name": "口径", "value": "DN15"}, {"name": "材质", "value": "不锈钢"}],
      "amount": 15000,
      "enabled": true
    }
  ]
}
```

编辑已有规格时保留其 `id`，新增规格使用 `0`。提交的是该内容的完整规格集合；移除的规格归档，保留 ID 和历史订单，不再接受新购买。分类和内容的销售能力不依赖栏目名、内容模型名或固定路由。

规格维度由独立后台页面 `/admin/commerce-dimensions` 统一维护，按站点隔离，定义保存在 `gocms_commerce_dimension`；产品的 `dimensions_json` 保存选用的定义及排列顺序。内容编辑只允许选择、调整选用顺序和取消引用，不提供维度名称、类型、单位和候选值的编辑入口，API 也拒绝通过内容保存创建或修改共享定义。示例中的维度 `key` 需替换为维度管理接口返回的真实值。

维度管理接口位于 `/api/admin/payments/dimensions`：GET 返回 `items`（定义、`version`、`product_count`），POST 新建；`/<key>` 的 PUT 修改，DELETE 带 `?version=<version>` 删除。读取和内容选用需要 `payments`；新建、修改和删除另需 `payments.configure`、后台登录会话及同源请求。写入校验版本，防止旧窗口覆盖其他管理员的修改。

修改维度名称、增加或删除未使用的候选值，会在同一事务内同步引用产品的定义和当前 SKU 参数名称，保留规格 ID、编号、价格、固定币种价格和启停状态；历史订单及归档规格不改写。已引用的维度不能修改类型或单位，仍被当前规格行使用的候选值不能删除，引用数大于零的维度不能删除。需要改变类型或单位时，新建维度并按产品调整。后端同时校验每行覆盖所有选用维度、选项值属于候选集、数字格式有效，单位由共享定义写入 `specifications[].unit` 并进入订单快照。规格值继续使用名称和值兼容已有主题、购物车和订单，单位不参与组合定价运算。

“补全选项组合”仅适用于全部为选项类型的维度，按候选值生成缺失组合，保留已存在行的 ID、SKU、售价、固定币种售价及启停状态。新组合价格留空，需填写后保存；只售卖部分组合时可手动添加或移除行，无需覆盖全部笛卡尔积。生成超过 500 种时会提示缩减候选值或手动录入，服务端也限制 500 行。已有但尚未填写新增维度值的规格行会保留，需要手动补齐或移除，避免把旧价格自动分配给某个新组合。移除维度如将产生重复组合，后台要求先整理行；不自动合并不同价格。

销售配置统一使用共享维度库。内容保存提交完整的 `dimensions` 和 `variants`，无规格商品使用 `dimensions: []`，有规格商品必须先在维度管理中创建定义，再在内容中选用。每个规格行须填写全部选用维度的值。共享名称、类型或单位更新后，未刷新的内容编辑窗口会收到冲突提示，需重新打开后编辑，不能通过内容保存覆盖共享定义。

已有主题可继续读取 `specifications`；带 `content_id` 的公共目录响应另返回产品选用的 `dimensions`（仅在有可售行时），便于主题按顺序和单位渲染。目录仍每页最多 50 行，产品页需翻页读取全部组合；一个订单最多 50 个不同规格的限制保持不变。历史订单的规格、单位和金额快照不会因编辑产品改变。

商品销售配置统一通过内容编辑维护，后台不提供独立“售卖项”列表。`GET /api/admin/payments/offers` 可读取未归档规格，POST／PUT 写入返回 409 并提示使用内容编辑。商品必须有内容销售配置，并满足内容公开、分类开启销售及规格启用等条件后才能购买。

## 状态与扩展边界

订单状态为 `unpaid → paid → refunded`，交付状态独立保存。一次订单可有多次支付尝试，但只允许一笔处于待确认状态；PingPong 默认收银台的 `FAILED` 仍可继续支付，不能据此新开交易。已关闭尝试可以重新付款。后到的失败通知不会覆盖成功；极端情况下多笔尝试都成功时，只生成一次付款交付事件，额外收款在后台标记，需要人工退款。

通知先校验 v4 SHA256 签名、商户身份、交易编号、金额、币种及第三方交易号，再在同一数据库事务内更新支付、订单、去重事件及 outbox。浏览器回跳不作为到账依据。后台进程启动后及每分钟批量补查到期的支付和退款记录；失败通常延后约两分钟继续查询。此补查用于交易状态恢复，不等同于银行结算账单核对。outbox 当前用于保存付款及退款事件、支持人工交付记录，没有自动执行业务权益的消费者。

实现分为 `internal/commerce`（内容交易配置、规格、订单及状态流转）与 `internal/payment`（统一 Provider 接口）；PingPong v4 实现在 `internal/payment/providers/pingpong`。新增服务商时实现验证、创建、查询、退款、退款查询和通知解析，注册到服务端并补充后台配置字段及对应契约测试；订单和主题 API 可继续复用。模块随 GoCMS 单体部署，SQLite 保存重试计划，无需额外队列服务。

仓库中的自动化测试使用签名报文和模拟 HTTP 服务，场景包括防篡改、幂等、并发、站点与会员隔离、状态单调性及退款；未使用真实商户凭据。本次按要求未执行测试或构建。完成沙箱与生产商户联调后再开放实际收款。

## 后台准备顺序

1. 超级管理员生成或导入支付加密密钥，下载密钥备份；已有环境变量部署可直接接管。
2. 手动填写或导入 PingPong 渠道配置，核对通知地址与返回路径。
3. 在分类开启在线销售，为原内容设置封面、规格参数及各规格价格，开启内容销售并公开内容。
4. 使用 `/shop/` 购物前台，将渠道返回路径设为 `/shop/orders`；需要主题入口时在主题中添加购买链接。自定义主题购买页仍可安装和绑定模板再发布。
5. 使用真实商户沙箱参数完成支付和退款联调，再新建并启用生产渠道。

分类模板下拉框按主题分组优先排序，并允许选择当前主题的全部已安装模板，无需按照文件名重命名购买模板。以上 GoCMS 业务配置和资源操作均可从后台完成。PingPong 的商户申请、参数申请和支付方式开通仍在服务商平台办理。


## 基准币种与多币种定价

「支付管理 → 币种与汇率」按站点配置任意已支持币种作为基准，支持手动汇率、有效期、国家推荐映射及 JSON 配置导入导出。新商品与新渠道默认使用站点基准；既有商品和渠道不自动改币种。规格可覆盖各币种固定售价，未覆盖时使用交叉汇率。报价、前台偏好、支付能力校验和订单快照的完整规则见 [购物前台：多币种报价](storefront.md#多币种报价)。

开放展示某个币种不会自动开通该币种的 PingPong 收款能力。没有已启用的相应币种渠道时，前台显示目标币种参考价，同时明确实际支付币种。只有配置并启用了对应币种渠道后，服务端才将报价转换为该币种成交订单；渠道实际支持范围仍以商户开通情况为准。原有单币种支付校验、验签及退款流程继续使用订单锁定金额。
